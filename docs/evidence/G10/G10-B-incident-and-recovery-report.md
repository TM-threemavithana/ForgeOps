## 1. Incident Root Cause Analysis (RCA)

### Incident Summary
During the initial execution of Gate G10-B (PR #32), the rehearsal API Deployment was updated with an immutable digest. However, after Argo CD synchronized the change, the newly scheduled Pod `forgetasks-rehearsal-api-59996d7cf4-bf254` entered a persistent `CreateContainerError` state:
```text
Error: failed to generate container spec: failed to apply OCI options: no command specified
```

### Forensic Diagnosis
Inspecting the pinned digest `sha256:09f46f0823b908b7c09584c6143f7b5b0c67566c397d1a0328b71b15d3a2dcd9` on GHCR via `docker manifest inspect` revealed:
- `mediaType`: `application/vnd.oci.image.manifest.v1+json`
- `artifactType`: `application/vnd.dev.sigstore.bundle.v0.3+json`
- `config.mediaType`: `application/vnd.oci.empty.v1+json` (size: 2 bytes, empty configuration)
- `annotations`: `dev.sigstore.bundle.predicateType`: `https://slsa.dev/provenance/v1`
- `subject.digest`: `sha256:0d2faee3fb0746be0557760a26118d5fa637609654028a7eaa573f09cbdca83b`

**Conclusion:** The digest pinned in PR #32 was not a container image, but an 11 KB **Sigstore SLSA provenance attestation bundle** artifact generated by GitHub Actions (`actions/attest-build-provenance@v2`). The container runtime (`containerd` via `kubelet`) rejected it because it lacks an OCI container configuration, entrypoint, and filesystem layers.

### Availability & High-Availability Safeguard
Due to Kubernetes `RollingUpdate` strategy (`maxSurge: 1, maxUnavailable: 0`):
- The existing healthy Pod `forgetasks-rehearsal-api-fb69d46cf-t4v75` remained `Running (1/1)` and serving traffic.
- Health checks on `http://<pod-ip>:8080/actuator/health` responded with `{"status":"UP"}` throughout the entire incident.
- Argo CD auto-sync was disabled (`automated.enabled: false`), preventing unmonitored cascade mutations.
- **Zero downtime** was experienced by the rehearsal service.

## 4. Preventive Action & CI Workflow Improvement Recommendation

### Root Cause in CI
In `.github/workflows/publish.yml`, the job concludes with:
```yaml
      - name: Attest build provenance (SLSA)
        uses: actions/attest-build-provenance@v2
        with:
          subject-name: ${{ needs.validate-release.outputs.canonical_image }}
          subject-digest: ${{ steps.publish-digest.outputs.digest }}
          push-to-registry: true
```
When this action pushes to GHCR, GitHub Actions displays the attestation's OCI artifact digest in the workflow summary / step output. If an engineer copies the digest from the bottom of the run or from the registry UI, they inadvertently select the attestation bundle instead of the container image.

### Recommendation
1. Update `.github/workflows/publish.yml` to write a prominent GitHub Step Summary (`$GITHUB_STEP_SUMMARY`) displaying a clear markdown box:
   ```markdown
   ### 🚀 GitOps Deployment Reference
   Use this digest in Helm values:
   `ghcr.io/tm-threemavithana/forgetasks-api@sha256:<PRIMARY_DIGEST>`

   ⚠️ Do NOT use the attestation artifact digest below for Kubernetes deployments!
   ```
2. In future release automation, pass the output `${{ steps.publish-digest.outputs.digest }}` directly to any automated PR or release notes generator, bypassing manual copying.
